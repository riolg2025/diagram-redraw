# diagram-redraw

> 把**别人画的图**，变成**你能讲、能改的图**。

用户是各行业的**售前**——以及研发、实施、运维，凡是写方案写文档要画图的人。

他们手上通常**没有一张干净的源图**，只有一堆不标准的存量材料：
旧 PPT 里的形状、SmartArt、PDF 里的图、一张截图、翻拍的照片，或者干脆只有一段文字。

他们需要的是一张**能进自己方案、能对着客户讲、能当场改**的图。

**而现在他们的做法是：截图，直接贴进方案。**

---

## 它和"AI 画图"不是一回事

市面上"AI 画图"一抓一把。这个项目做的是**另一半**：

> **读懂人画的那张图 —— 并且知道自己哪里没读懂。**

因为图要拿去给客户讲，**讲错了要担责任**。所以在这个项目里，
**"知道自己哪里不确定"比"画得好看"重要得多**——而且，"能改"比"像到某个百分比"重要得多。

## 目标：要覆盖什么

⚠️ **这是目标，不是现状。现状见下一节。**

| | 要支持 |
|---|---|
| **输入** | PPT 形状 / **SmartArt** / Word 里的图 / PDF / **截图** / 照片 / 一段文字 / 几份一起给 |
| **交付** | PPT 可编辑图形 / Word 图形 / SVG / 图片 / drawio / Mermaid |

**第一版正在做**：PPT 形状 + SmartArt + 截图 → PPT 可编辑图形 + SVG。

**目标是明确不做的**：不做图形界面和服务器、不追求像素级还原、**不修改用户的原文件**、不承诺"一键出图"。

完整的目标、范围、架构和还没定的事，都在 [`docs/需求与目标.md`](docs/需求与目标.md)。

---

## 现在这一版实际能做什么（v0.1）

给它一页 PPT，指定要哪一块，它会：

1. **先问你**：要理解的是哪一块、要重画的是哪一块
2. **读**，然后把读到的东西**标在原图上给你核对**（"这些我都看到了，对吗？"）
3. 把不确定的地方**问清楚**
4. **画**成 PPTX（可编辑形状+文字）和 SVG（矢量）
5. **自己渲染回去和原图比**，确认没画歪

## 现在这一版**不能**做什么

这一节比上一节重要。

**v0.1 只覆盖 PPT 里的原生矢量图。** 下面这些**目标里有、这一版还没做**：

- **位图页**（整页就是一张图）、**手绘照片**、**PDF 输入** —— 都不支持
- **Word 里的图** —— 不支持
- **自由曲线图形画不出来** —— 常见于图标。会被列进"画不出来"的清单，**不会假装画上了**
- **表格** —— 不支持
- 交付只出 **PPTX 和 SVG**（图片 / drawio / Mermaid 还没做）

**这几条是目标里也不做的：**

- **不做图形界面、不做服务器**（装完就在 Claude Code / Codex 里用）
- **不追求像素级还原** —— 判据是"能不能讲 + 好不好改"，不是差异百分比
- **不修改你的原文件**（永远新建一份）
- **不承诺"一键出图"**（用户必须参与讨论）

⚠️ **只在一份真实企业 PPT 的两个页面上验证过。** 机制是通用的，覆盖面很窄——
这正是这个项目反复栽的坑。

遇到不支持的输入，它会**直接说不支持**，而不是勉强画一个看起来像的东西。

## 核心不是代码

代码只是把两条纪律固化下来。**真正的资产是那两份文件：**

- **`reading-rules.md`** —— 怎么读一张人画的图。里面每一条都是踩出来的，注明了"怎么发现的"
- **`ask-when.md`** —— 什么时候有权打断用户。**四条出路里只有一条需要用户开口**

其中最重要的一条，也是这个项目存在的理由：

> **一张图里"没有文字的形状"，多半是作者故意留空的。**
> 它通常的意思是"这里放你自己定义的内容"。
> **填上名字，元素数没变，但图的定位被改了 —— 等于把作者的意图改了。**

这条是从一个真实案例里推出来的：一张图里"工具服务层/执行层"全部具名，
"流程引擎层"全部留空。分界线不是随机的——**列举的东西必须具名，结构性的东西必须留空**。
而单看那张图，你永远读不出这个区别，**只能靠对照**。

## 一个踩过的坑（示例）

**不要直接渲染 pptx。** 实测那份 PPT 直接渲染 6 页**全部是空白**（6 页字节数一模一样）。
必须先转 PDF、再从 PDF 取图。
所以 `render_pptx.py` 里固化的是这条弯路，不是最直的那条。

`reading-rules.md` 里还有 8 条同类的东西。

## 现在的状态

**v0.1：一个跑得通的原型 + 一份完整的方法论记录。**

### 量化结果（自己渲染回去、和原图逐像素差分）

| 测试 | 显著差异像素 | 说明 |
|---|---|---|
| **第 5 页 B 区**（通用脚本） | **7.7%** | 手工精修那版是 **7.1%** —— **泛化基本没损失** |
| 第 6 页整页（通用脚本） | 13.1% | 见下面拆解 |

**13.1% 里是什么**（按区域拆开）：

```
左侧流程图      13.2%
右上文字卡      15.7%   <- 文字密集
右侧上方        24.2%   <- 文字密集
右下截图区      11.2%
顶部标题条      13.6%
```

**差异是均匀铺开的，不是集中在某处** —— 说明是全局性差异：
**文字渲染**（渲染环境里没有 `微软雅黑`，被替换成别的字体）加上**边框 1px 取整偏移**。
文字少的地方差异明显更小（B 区 7.7%）。

**真正画不出来的那 8 个自由曲线图标只贡献 0.3 个百分点** —— 实测的。
我原以为它们是主因，**猜错了**。

### ⚠️ 但这个指标下一版要换掉

逐像素差分测的是"**渲染出来的图像有多接近**"，
而真正的风险是"**这张图拿去讲会不会出错**"。这两件事基本是**错开**的：

- **要命的错**（文字写错、箭头方向反、元素多一个少一个）在像素上**几乎看不见**
- **像素差的大头**反而是没人在乎的东西 —— **字体替换、1px 取整偏移**

上面那个 13.1% 拆开看就是这个样子：**主要是缺字体造成的全局性差异，不是理解错误。**

> **换句话说：继续压这个数字，产品上已经不产生价值了。**
> 而真正会出事的那几类错，它一个都测不出来。

下一版的判据换成**逐条对账**（输出 vs 清单、清单 vs 原件）——文字那一块可以做到
**全机器验证、完全不经过 AI 的眼睛**。理由和做法见 [`docs/需求与目标.md`](docs/需求与目标.md)。
