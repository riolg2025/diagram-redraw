## 一、实测：SmartArt 到底能不能读

**样本**：一份真实企业 PPT 的第 2 页（5 层 chevron + 5 个圆角矩形）
**产物**：本地 `smartart-test/`，对比图 `smartart-对比.png`（**含真实公司材料，未入库**）

### 结果一：SmartArt 的版面**在文件里**（原来的判断是错的）

`ppt/diagrams/drawing1.xml` 里存着**10 个形状的完整信息**：

| 有什么 | 例子 |
|---|---|
| **形状类型** | `prstGeom prst="chevron"` / `"round2SameRect"` |
| **精确坐标和尺寸** | `a:off x="-240032" y="245283"` / `a:ext cx="1542848" cy="1062783"` |
| **旋转** | `rot="5400000"`（90°） |
| **颜色** | `schemeClr val="accent4" lumMod=60% lumOff=40%` |
| **文字** | "1.资源层（应用CMDB）" |

**决定性验证**：把这个部件里第一个 chevron 改成红色、第三个改成绿色 → **重新渲染，颜色跟着变了**。
→ 证明渲染器（LibreOffice）**确实在读这个缓存版面**，不是自己算的。

### 结果二：没有缓存时，渲染器算出来的版面**是错的**

把 `drawing1.xml` 和它的关系引用删掉再渲染：

| | 有缓存 | 没有缓存 |
|---|---|---|
| 五个 chevron | 均匀分布，撑满整页 | 间距错乱，缩在页面上半部 |
| chevron 形状 | 完整的向下箭头 | 画成 V 形碎片 |
| 文字 | 在形状内 | 溢出到形状外 |
| 整页范围 | 收在页面内 | **溢出页面底部**（第 5 层被切掉） |

**但整页像素差异只有 7.74%** —— 这就是下面的坑 A。

### 结果三：缓存版面的覆盖率是 100%

扫了桌面 **40 份真实 PPT**：

```
带 SmartArt 的文件：24 份
SmartArt 总数：123 个
其中带缓存版面的：123 个（100%）
```

→ 这些文件都是微软 Office 存的。**风险不在"常见不常见"，在"来源不明的文件"**（客户转发、第三方工具另存、在线转换过的）。

### 净结论

| 判断 | 结果 |
|---|---|
| 我原来说"SmartArt 的版面不在文件里" | ❌ **错的，撤回** |
| 我原来说"渲染 SmartArt 可能不准" | ✅ **对，但只在缺缓存时**；而且要担心的不是"不准"，是**"错了还查不出来"** |
| 入4 的难度 | **从 ★★ 下调到 ★**——有缓存时它是**最好读的输入**：形状类型是明写的（普通 PPT 形状的名字会骗人），坐标是精确的，**还额外多一份 `data1.xml` 给内容和层级**（谁属于谁、分几级），这是别的输入都没有的 |

### 附带发现：坑 A —— 逐像素差分对"渲染器自己的错误"免疫

读图和自检用的是**同一个渲染器**。所以渲染器犯的错，会**在原件和重画件上同时出现，被差分直接抵消**。

**实测数据**：把一份 SmartArt 的缓存版面删掉，渲染出来的图**完全错乱**，但整页的**显著差异像素只有 7.74%**——**低于"超过 15% 就别交付"的阈值**。

> ⚠️ **一份明显画错的图，能顺利通过"渲染回去对比"这道自检。**

**这条不是 SmartArt 专属的。** 任何"AI 看得对不对"的问题，都不能只靠"渲染回去比一比"来回答，因为**看和验是同一双眼睛**。

→ 决策文档 §十.5 的 Check A / Check B 就是冲这个来的。

### 附带发现：坑 B —— 那个缓存只有微软 Office 存的文件才有

`ppt/diagrams/drawing1.xml` 是**微软的扩展部件**（`xmlns:dsp=".../office/drawing/2008/diagram"`），**不在 OOXML 标准里**。

- **有它** → 形状类型、精确坐标、旋转、颜色、文字**全都在**，直接读，最准
- **没有它**（WPS / LibreOffice / 第三方工具存的）→ 渲染器只能**自己算版面**，**实测算出来是错的**

→ 所以读完一份 SmartArt 之后，**必须先探测有没有这个部件**，再决定信不信渲染出来的样子。

## 二、实测：SVG → PPTX 这条转换路走不通

**目的**：验证"**先画 SVG，再转成 PPT 图形**"这条路。
**样本**：`examples/dryrun-02/slide5-B-redraw.svg`（一份真的重画产物）　**产物**：本地 `draw-test/`（未入库）

### 三条路都试了

| 尝试 | 结果 |
|---|---|
| 项目自己那套 LibreOffice kit | ❌ `unsupported-format: svg → pptx` |
| 系统 LibreOffice 直接转 | ❌ Draw 文档没有 pptx 导出过滤器 |
| 绕道 SVG → ODG（这一跳成功） | ⚠️ **转出来是一张图片** |

### 第三跳的详细结果

```
来源 SVG：  21 rect + 16 line + 2 polygon + 2 ellipse + 8 path + 24 text
导入结果：  0 个可编辑形状
            2 个 draw:image  +  1 个 draw:frame
            （还顺手栅格化了一张 PNG 塞进去）
```

**这就是这个产品最想避免的结果：SVG 一进 PPT 就变成一张死图。**

### 而且就算它按形状导进去了，也不解决问题

SVG 里的信息不足以还原"预设形状"——一个圆角矩形的路径**反推不回**"圆角矩形"，只能变成自由曲线。用户点开一看是一堆节点，**还是改不动**。

> 用户要的"可编辑"是"**点开一个矩形，改文字、拖大小**"，
> 不是"有一堆可以拖的节点"。这两件事差得很远。

### ⚠️ 但这个结论有边界

它否定的只是「**通用** SVG → PPTX」（从路径反推形状）。
**「受约束的中间格式 + 显式语义标记」那条路是走得通的**——见 §四，两个成熟项目都这么干。

## 三、现状记录：现在"画"是怎么实现的

> 记录的是**某一版的快照**，不是路线。目的：以后讨论时知道起点在哪。

**两条独立的序列化路径，各自遍历同一份清单，中间没有任何转换。**

```
            spec.json（清单）
            │              │
      build_pptx()     build_svg()
       python-pptx      手拼 XML 字符串
            ▼              ▼
         out.pptx       out.svg
```

**但两条路的"活儿分布"完全不同：**

| | PPTX 那条 | SVG 那条 |
|---|---|---|
| `upDownArrow` | `MSO_SHAPE.UP_DOWN_ARROW`，**一行** | **30 行手写路径** |
| 大括号 | `MSO_SHAPE.LEFT_BRACE`，**一行** | **10 行手写路径** |
| 文字换行 | **交给 PowerPoint**（`word_wrap` + 文本框内边距） | **自己算** |
| 行距 / 垂直居中 | **PowerPoint 自动** | **硬编码经验系数**：行距 `×1.15`、居中 `0.58 / 0.35` |
| 坐标 | EMU，交给库 | 每一个数字自己拼 |

**这不是实现问题，是格式本质：**

| | PPTX / DrawingML | SVG |
|---|---|---|
| 预设形状库 | **182 种**（python-pptx 现成可用） | **没有**，只有 rect / circle / line / path |
| 文字排版 | **自动**（换行、居中、自动缩放） | **没有**，一行一行给坐标 |
| 主题色 | 有（`schemeClr`） | 没有，只能绝对色 |
| 语义 | 连接线有端点、形状有名字 | 基本没有，就是一堆路径 |
| 坐标单位 | EMU | px |

> **PPTX 是"声明式"的**——你说要一个圆角矩形，位置和文字它帮你摆。
> **SVG 是"命令式"的**——每一根线、每一行字的坐标，都得你算。

### 顺带发现一个违反自己规矩的地方

SVG 侧**没有任何换行计算**——它直接把清单里的 `\n` 当换行。也就是说，"**这一行字在哪儿断**"是在"读"那一步就定死的，**被藏进了 `text` 这个自由文本字段里**。

这正好违反决策文档 §十 定的那条 **"承重信息不许放自由文本字段"**——换行位置是层 2 的信息，它应该有自己明确的位置。

### 一个依赖事实

`svg2png.py` 用的是 **Chrome headless**（`--headless=new`）。
（本机探测：rsvg-convert / inkscape / cairosvg 都没有，qlmanage 被沙箱挡住，Chrome 可用。）

它开头写着为什么必须有它：

> "LibreOffice **不支持 svg -> 图**，所以 SVG 一度是'**我交出去但自己看不见**'的东西，**连着错了两次**（箭头没头、大括号画错）。"

## 四、外部项目调研

**目的**：搞清楚"画"这块，哪些该自己写、哪些有现成的。

### 结论一：187 个预设几何，不要自己写

| | |
|---|---|
| **是什么** | **187 个** DrawingML 预设形状的几何定义 |
| **哪来的** | `presetShapeDefinitions.xml`，vendored from **Apache POI 5.4.1**（Apache-2.0）；配套枚举来自 `dotnet/Open-XML-SDK`（MIT）。**有 NOTICE、有 hash 锁定** |
| **配套还有什么** | 公式求值器（算 `*/ h adj1 100000` 这类 DrawingML guide 公式）、注册表（`evaluate("rightArrow", 320, 160)` → 直接拿路径命令，**纯标准库**）、以及一份给 AI 用的**语义词表** |
| **在哪** | `hugohe3/ppt-master` → `skills/ppt-master/scripts/pptx_shapes/` |
| **我们现状** | 只映射了 **11 种**，而且 SVG 侧每一个都要手写路径（见 §三） |

→ **自己写 187 个不划算，直接复用这份数据。**（拿数据，不一定要拿架构。）

### 结论二：两个成熟项目，路线不同，套路相同

| | **ppt-master** | **presenton** |
|---|---|---|
| 中间格式 | **项目规范化 SVG** | **自己的 HTML**（幻灯片编辑器产出的） |
| 语义怎么带 | `<g data-pptx-authoring="preset" data-pptx-prst="rightArrow" data-pptx-frame="x y w h">` | 元素上的标记 |
| 谁算排版 | 自己没有排版需求（版式是它设计的） | **Chromium**（当排版计算器） |
| 产出 | 原生 DrawingML（`a:prstGeom` / `a:custGeom`） | 原生形状（**已确认可编辑**——用户实测用过） |
| 反向 | `pptx_to_svg.py --roundtrip` | `convert_pptx_to_html` / `_to_json` |
| 有没有 Chromium | 不需要 | **需要** |

> **两个都不是"通用格式转换"，都是"自己的中间格式 + 显式语义标记"。**
> **中间格式长什么样（SVG 还是 HTML）不重要——"带不带语义标记"才是关键。**

⚠️ **ppt-master 有一条关键硬规矩**：

> **"Never infer a preset"** —— 形状"**只是像**"某个预设时，**不许认**。
> **"Export never scans or upgrades existing geometry"** —— **转换阶段从不猜形状。**

**这条对我们要改一下再抄**，因为我们的场景不同：

> **能读到的就读**（原件是 PPTX / SmartArt 时，`prstGeom` 是明写的，不用猜）；
> **读不到才推**（图片输入），而且推出来的**必须标成"我推的"**。
> **但序列化阶段绝不引入新的判断。**

这正好接上决策文档 §十 的层 1 / 来源标记——**推断只允许在"读"那一步发生，而且必须留痕**。

### 结论三：SVG 的真正好处是"看得见"，不是"写得省事"

ppt-master 排除其他方案的原话（值得留着）：

| 被排除的 | 理由 |
|---|---|
| **直接生成 DrawingML** | "极其繁琐，一个简单的圆角矩形就需要**数十行嵌套 XML**，AI 的训练数据中远少于 SVG，生成质量不稳定，**调试几乎无法肉眼完成**" |
| **HTML/CSS** | "HTML 描述的是**文档**（位置由内容流动决定）；PowerPoint 描述的是**画布**（每个元素独立、绝对定位，没有流）。这不只是排版计算的问题，而是**两种内容组织方式之间的鸿沟**" |
| **WMF/EMF** | "理论上转换损耗最小，但 AI 几乎没有训练数据，**这条路死在起点**" |
| **SVG 当图片嵌** | "完全丧失可编辑性，**和截图没有本质区别**" |
| ✅ **SVG** | 与 DrawingML **同一个世界观**：绝对坐标的二维矢量，概念一一对应 |

它给的最关键一条：

> "SVG 是**唯一同时满足流程中所有角色需要**的格式：**AI 能可靠地生成它，人能在任意浏览器里直接预览和调试，脚本能按明确的兼容合同转换它**——在生成任何 DrawingML 之前，**设计稿就已经完全透明可见**。"

⚠️ **但"画 SVG 很麻烦"要分情况，不能一概而论：**

| | ppt-master 干的 | 我们第一版干的 |
|---|---|---|
| 版式从哪来 | **它自己设计** | **原图给定** |
| "每行字自己算坐标" | **不是问题**——自己定的不用算 | **是问题**——要精确复刻 |
| SVG 的角色 | 设计稿 + 中间语言 + 交付物 | **只是交付物** |

**同一个格式，在两种场景下好坏相反。**

### 结论四：为什么第一版不改路线

我们的 `spec.json` **已经是**那份"带语义标记的中间格式"了，而且标得比 SVG / HTML 更彻底——它连"**这条信息是原件读到的、我推的、还是用户说的**"都标了。**这个 SVG 和 HTML 都装不下。**

**但有一处差别是真的：**

| | `spec.json` | SVG / HTML |
|---|---|---|
| 机器能读 | ✅ | ✅ |
| **人能不能直接看** | ❌（所以我们要 `spec.md` + 标号图来补） | ✅ **直接就能看** |

他们**一份顶两份**，代价是必须**打标记 + 写合同 + 做检查器 + 写回归测试**（ppt-master 为这件事写了一整套合同文档和前置质量门）。

我们的分工是：**`spec.json` 给机器，`spec.md` + 标号图 给人。** 这也成立，而且**更适合"从原图抄"**。

> **两条路都对，选哪条取决于：版式是"自己设计的"还是"给定的"。**

### 结论五：什么时候要重算

⚠️ **如果以后支持"从零画"（入6），或者要做 Mermaid 输出（需要自动排版），这一节的结论要重估一遍。**

那时我们的处境从"版式给定"变成"版式自己设计"，**SVG 当中间稿的好处会全部回来**：一份顶两份、人直接能看、AI 生成最顺。而且 **Chromium 已经在手上了**（见 §三），那条路的两块砖其实都有了。

## 六、实测：四轮真实反馈里，用户到底报了什么

**来源**：`examples/dryrun-01/README.md` 和 `examples/dryrun-02/README.md` 里逐轮记下的用户反馈。
**为什么值得挖**：这是这个项目**唯一的一手用户反馈**，而且它能直接检验「容忍度不对称」这个假设。

### 全部 7 条反馈

| # | 用户报的 | 来自 | 类别 | 像素差抓得到吗 |
|---|---|---|---|---|
| 1 | 步骤 6 应该写「**测试环境**」不是「开发环境」 | dryrun-01 第 4 步 | **内容**（而且是**原件自己的错**，问了用户才改） | ❌ **抓不到，而且会判反**——见下 |
| 2 | 那个**朝下的箭头要保留**，它代表双向关系 | dryrun-01 第 4 步 | **关系**（元素少一个） | 🟡 很弱 |
| 3 | "**SVG 也不错**" | dryrun-01 第 4 步 | ✅ **正面评价** | —— |
| 4 | **文字压住边框** | dryrun-02 第 3 轮 | 外观**症状**，根因是**描边宽了一倍**（0.9pt vs 原图 0.5pt） | ✅ 能 |
| 5 | **SVG 和预览不一致**（箭头全没了、字号小三成） | dryrun-02 第 3 轮 | **输出缺失 / 不一致** | ✅ 能（当时没有 SVG 渲染能力，是靠 grep 数出来的） |
| 6 | **K1/K2 大括号不对** | dryrun-02 第 4 轮 | **形状** | ✅ 能 |
| 7 | **Y1 / W1 / W2 双向箭头画成了单向** | dryrun-02 第 4 轮 | **关系 / 方向** | ❌ **几乎抓不到** |

### 三个结论

**① 6 条问题里，0 条是审美。**

用户从没抱怨过配色、排版、好不好看。dryrun-01 里他甚至明确说"**配色我定**"——把审美权直接交出去了。
唯一一条看起来像外观的（#4 文字压边框），**根因还是"画错了"**：线宽错一倍。

→ **审美不是这个产品的主要风险面。** 这个判断现在有一手证据了。

**② 最要命的两条，恰好是像素差抓不到的那两条。**

#1（内容错）和 #7（关系错）——正是「错误类型表」里排最前的两类，**也正是逐像素差分测不出来的**。

**③ 而 #1 更狠：像素差不但抓不到它，还会把它判成"错误"。**

```
原件写：  6. 部署到「开发环境」
但它站在「测试环境」上方 → 按规矩原样照抄 + 告诉用户
用户确认：改成「测试环境」
```

改完之后，**输出和原件就不一样了**——差异从 0% 变成非 0。
也就是说：**逐像素差分会把这次"改对了"记成一次退步。**

> ⚠️ 这一条直接印证了决策文档 §十.5 里那条设计：
> **Check B 只对"标为来自原件"的条目做对账。**
> 而这条的标记已经变成「用户说的」——**它根本不会进入 Check B**，因此不会被误判。

### ⚠️ 但这份证据证明不了的事（很重要）

| 它证明了 | 它**没有**证明 |
|---|---|
| 用户**报出来**的问题，几乎全是要命的那几类 | **容忍度**——只测了"报什么"，没测"忍了什么"。他可能默默忍了十处不好看 |
| 审美不是主要风险面 | 这是**独立售前**的判断——样本就是项目作者本人，不是第三方售前 |
| 内容/关系错是真实发生过的 | **拿去给客户讲之后**会怎样——这些反馈都发生在"检查"环节，不是"用"的环节 |

**所以第 1 条待定（🔴"多像才算够"）仍然没被解决**，只是被缩窄了：
现在的问题不再是"要多像"，而是——

> **真实售前在什么情况下会默默忍、什么情况下会当场翻脸？** 这个还是一片空白。
