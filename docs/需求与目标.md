# 需求与目标 —— 对齐稿

> 这份文档记录**讨论对齐的结果**，是**决策文档**：需求、架构、已定的选择、还没定的事。
> 区分三件事：**已定** / **未定** / **我方判断（可推翻）**。⚠️ 标的是**容易被忘记、或容易想当然**的地方。
>
> **证据不在这里。** 实测记录、外部调研、现状快照都在 [`实测与调研.md`](实测与调研.md)。
> 分开的理由：证据**不会被"改主意"作废**，但也不该混进决策里搅局。

---

## 一、这是给谁用的、解决什么

**用户**：各行业的**售前**，以及其他技术同事——研发写设计文档要画、实施交付要画、运维排障也要画。

**画什么**：流程图 / 架构图 / 示意图 / 泳道图 等。

**怎么画**（同一个人在不同场合用不同画法，这些是**真实并存**的）：

- 在 PPT 里用**形状**画
- 用 **SmartArt** 画
- 用 **drawio / Visio** 画
- 写 **Mermaid**
- 直接**截图 / 贴图**

⚠️ **这些图经常不是从头画的**，是拿现成的改——客户给的、竞品扒的、上一版方案里的。

---

## 二、画图这件事，实际的几种起点

### 原始的三类

1. 手上**没有现成的** → 根据文档或脑子里的思路**从零画**
2. 手上有**现成的、可编辑的** → **拿来改**，或者**直接截图用**
3. 手上有**现成的、不可编辑的（图片类）** → **直接用**

### 按"动作"归并，其实是三条路

| 动作 | 说明 |
|---|---|
| **从零画** | 起点是文档 / 想法 |
| **拿现成的改** | 起点是材料 |
| **不画，贴上去** | 第 2 类的"截图用"和第 3 类的"直接用"是**同一个动作** |

### 常见的变体

- **要拆**：现成的图里只有一块是我要的（一大张里只要左下角）
- **要合**：没有一张完整的，得从几个来源凑（自己的半张 + 客户给的半张）
- **要改的原因不只是"内容不对"**：过时了要更新、有敏感信息要去掉、风格不搭要统一、竞品 logo 要换掉——**内容一个字没改，但不改就没法用**

⚠️ 这几个变体的共同点：**卡住人的不是"画"，是"判断"**——判断要哪一块、判断哪里不能给客户看。

## 三、图会用到哪里（用法）

1. **放进 PPT**（最常见）
2. **放进各类 Word 文档**（产品文档、方案、标书）
3. **直接截图发给客户或同事**
4. 还包括：**在线文档 / wiki**（Confluence、飞书、钉钉、Notion）、**代码仓库 / README**、**画图工具的源文件**（留着以后再改）、**打印出来的标书**

⚠️ 区别很关键：**1 和 2 里图能保持是"活的"**（点开还能改）；**3 必然是"死的"**（发出去就是一张图片）。

⚠️ 还有一个模式比单个"终点"更常见：**同一张图要出好几个形态**——先在 PPT 里画好 → 截图发群里 → 再贴进 Word 标书 → 下次汇报再拿出来改。**一张图不是"一个用法"，是一路用下去。**

## 四、前提：AI 现在具备什么

### 1. 有排版和画图能力——但三条路性质不同

| 方式 | 能精确控制吗 | 能复现吗 | 输出可编辑吗 |
|---|---|---|---|
| 模型**原生生成图片** | 不能，靠运气 | 不能 | 不能 |
| **写代码**生成（Python 画 / 写 SVG / 生成 pptx） | **能** | **能** | **能** |
| 交给**第三方布局**（graphviz / mermaid / ELK） | 布局由它定 | 能 | 看目标格式 |

**只有中间那条能同时做到"精确 + 可复现 + 可编辑"。**

### 2. 能转成不同格式——但"转换"其实是"重新表达"

- **矢量 → 位图**（svg → png）：便宜、单向、不可逆
- **位图 → 矢量**（png → svg）：**这不是转换，这是重画**
- **语义格式之间**（svg ↔ pptx ↔ drawio）：能做，但**语义要重建**——PPT 的形状有名字、有主题色、有层级；SVG 里只剩路径

### 3. AI 画过一次的图，以后更容易理解和修改

**成立，而且这是相对于"人画的图"而言的。** 一句话：

> **人画的图，AI 得猜；AI 自己画的图，AI 本来就知道。**

人画的图上，每一样东西都要重新推：这个形状是什么（名字会骗人）、这两根线连的是谁（可能根本没有端点）、这个空框是没画完还是故意的。

⚠️ **前提是留下了"结构化的源"。** 渲染出来的 PNG / PPTX 是**结果**，下次还得重读；对话记录也不是可执行的源。**源一丢，自己画的图就退化成"人画的图"，又得从头猜一遍。**

⚠️ 反向风险：**如果留下的是 AI 的"理解"，而那个理解本身就是错的，下次就是在错的上面改，错误会被固化。** 所以关键不只是"留不留源"，而是**源里要分清哪些是原件的、哪些是 AI 推的**。

## 五、产品是什么：一条流水线

```
① 输入 ←──────────────────┐
      ↓                     │
② 理解 + 讨论确认            │  用户补充材料
      ↓                     │
③ 排版 + 画图               │
      ↓                     │
④ AI 自检                   │
      ↓                     │
⑤ 交付                     │
      ↓                     │
⑥ 用户验收 ────有意见────────┘
```

| 步 | 做什么 |
|---|---|
| ① | 收材料：ppt / 图片 / 文档 / 用户描述等，**可以多种一起给** |
| ② | **读懂素材 + 读懂意图 + 和用户对清楚**，确保理解一致 |
| ③ | 排版 + 画图 |
| ④ | **AI 自检** |
| ⑤ | 交付（PPT / SVG / …） |
| ⑥ | 用户验收，有意见就回到 ② |

### 关于这个环的三件事

1. ⚠️ **环可以是 1→6，但大部分时候是 2→6。** 输入只发生一次；多数情况下从第二轮开始就**不重新读原件**，而是在**已经确认过的那份理解**上继续改。
2. ⚠️ 所以**那份"已确认的理解"必须留下来，并且必须是可增量的**——新素材要能挂到已有理解上，而不是每来一份就推翻重来。
3. ⚠️ 副作用：**补进来的材料可能推翻已经确认过的结论**（比如新给的一张图说明之前那个空框其实有内容）。这时候必须**回头把那一处重新确认**，不能拿旧结论继续往下画。

## 六、要覆盖哪些场景：主要是第 ① 步和第 ⑤ 步

**支持面 = 输入 × 交付，可以不断丰富。** 这正是"不要被现有产出物锚住"的正确含义——**产出物是某一版的快照，场景是一直在长的**。

但有三条判断：

1. ⚠️ **① 和 ⑤ 不对称**：

   | | 每加一种，是什么性质 | 成本 |
   |---|---|---|
   | **第 ⑤ 步（交付）** | 同一件事**换个出口** | 低，可以铺得快 |
   | **第 ① 步（输入）** | 一种**新的感知问题** | 高，得一个一个啃 |

   因为第 ① 步每加一种材料，**丢的东西都不一样**：PPT 丢语义（名字会骗人）、矢量 PDF 丢名字和层级、图片丢几何和结构、纯文字丢几何。

2. ⚠️ **① 和 ⑤ 是接口，②③④ 才是产品。** 无论什么格式进来出去，都必须走第 ② 步。**这一步做不好，加多少格式都是白加**——只是多了几种方式把图理解错。

3. ⚠️ **"不断丰富"需要一个收敛规则**，否则会变成"不断分叉"：每来一个场景就加一套专用行为，最后互相打架。
   **规则：每加一个场景，必须能说清它相对于已有场景"多丢 / 多得了什么信息"，以及"多了哪一步确认"。** 说不清的，就是重复建设。

### 读这份清单的镜片

> 用户手上有现成材料时，**"可编辑的"那一半，他自己就能动手改**——改个颜色、挪个框，不需要 AI。
> **"不可编辑的"那一半，才是非 AI 不可。**
>
> 所以不是越"高级"的材料越值得做，是**越"死"的越值得做**。

### 第 ① 步：输入清单

按"还剩多少信息"排，从好办到难办。

| 编号 | 是什么 | 最麻烦的地方 | 难度 |
|---|---|---|---|
| **入1** | drawio / Visio 源文件 | 各家格式不同 | ★ |
| **入2** | PPT 里用**形状**画的图 | **形状的名字经常是错的**（叫"右箭头"其实指向左） | ★ |
| **入3** | Mermaid / drawio 的代码文本 | —— | ★ |
| **入4** | **SmartArt** | 版面**其实在文件里**；**但只有微软 Office 存的文件才有**，缺了渲染器就会算错 | ★（见 [实测一](实测与调研.md)） |
| **入5** | Word 文档里的图 | 分形状 / SmartArt / 图片三种，取出来麻烦 | ★★ |
| **入6** | 用户的一段**文字描述** | **只有想法，没有形状和位置**；描述往往残缺 | ★★★ |
| **入7** | PDF 里的图 | 位置很准，**但什么名字都没有**，分组层级全丢 | ★★★ |
| **入8** | **一张图片 / 截图** | **只有像素**；形状、文字、连线全靠猜 | ★★★★ |
| **入9** | 手机拍的照片 | 比截图还难：歪的、有反光、有透视 | ★★★★★ |
| **入10** | 好几份材料一起给 | **材料之间会打架**，得判断以谁为准 | ★★★★ |

⚠️ **入6 = "从零开始画"那一路**（用户手上没有图，只有文档或想法）。

### 第 ⑤ 步：交付清单

| 编号 | 是什么 | 用户能接着改吗 | 常见用途 |
|---|---|---|---|
| **出1** | **PPT 里的图形** | **能**，点开就改 | 做方案、汇报 |
| **出2** | Word 里的图形 | **能** | 产品文档、标书 |
| **出3** | drawio 源文件 | **能**，留着以后接着改 | 以后再编辑 |
| **出4** | **SVG** | 能，但不如 PPT 顺手 | 网页、印刷、放大不糊 |
| **出5** | PNG / JPG | **不能，死的** | 发微信、贴邮件 |
| ~~出6~~ | ~~PDF 里的图~~ | **已撤回**，见下 | —— |
| **出7** | Mermaid 文本 | 能改文字，**但版面它说了算** | 代码仓库、技术文档 |

#### 为什么撤回出6

**PDF 不是一个独立的交付格式。** 放进了 PDF 就动不了了——PDF 里的图形要么是一堆没有名字的线条，要么是一张嵌入的图片，**改不了**，跟"可编辑"这条主线相反。

拆开看只有两种含义，都不成立：

- 把图画在一页 PDF 上 = **出4 或出5 外面包一层壳**
- 把图插进用户已有的 PDF 里 = 这是"**送到哪**"的问题，不是格式；而且 PDF 不是为编辑设计的

### 送到哪（不是格式）

| 编号 | 是什么 |
|---|---|
| **送1** | 新建一个文件给用户 |
| **送2** | 直接插进用户指定的那份 PPT / Word 的某个位置（以后） |

## 七、第一版范围（已定）

> **入2 + 入4 + 入8 → 出1 + 出4，走送1**

即：**3 种输入 × 2 种交付 = 6 个组合。**

| | 选了什么 | 为什么 |
|---|---|---|
| 输入 | **入2** PPT 用形状画的 | 最常见，信息最全，当保底 |
| 输入 | **入4** SmartArt | **在 PPT 里非常常见**（实测 40 份 PPT 里 24 份有，共 123 个）；而且**内容和版面都真记在文件里**，是最好读的输入之一 |
| 输入 | **入8** 一张图片 / 截图 | **最痛**——现状就是它；也只有它能验证"把死的变活" |
| 交付 | **出1** PPT 可编辑图形 | 售前最常用 |
| 交付 | **出4** SVG | 几乎是白送的 |
| 送到哪 | **送1** 新建文件 | |

⚠️ 第一版的目的不是"支持得多"，是**验证那条唯一非 AI 不可的路走不走得通**。
⚠️ 入8 是清单里第二难的，放进第一版有风险。但不放进去，第一版就证明不了任何有价值的事——因为"改可编辑的图"这件事，**用户自己就能做**。

## 八、明确不做

| | 不做什么 |
|---|---|
| ❌ | **不做图形界面、不做服务器**（装完就在 Claude Code / Codex 里用） |
| ❌ | **不追求像素级还原**（判据是"能不能讲 + 好不好改"，不是差异百分比） |
| ❌ | **不修改用户的原文件**（永远新建一份） |
| ❌ | **不承诺"一键出图"**（用户必须参与讨论） |

## 九、几条设计原则（不是硬要求，可以按情况落地）

### 1. 风险可见

> **图上任何一条信息，都要说得出它是从哪来的；来源越弱，标得越显眼、越容易被用户当场改掉。**

来源分档（沿用已有做法）：**原件明写 / 我量出来的 / 我拼出来的 / 我推的 / 行内常识补的**。

⚠️ 这条**不写成硬要求**——不同画法可以自己决定怎么落地。

### 2. 打败的是"截图"，不是别的 AI 画图工具

**用户现在的做法是：截图 / 原图直接贴进方案。** 所以这是一笔交换：

> **用"可能读错"的风险，换"能讲 + 能改"。**

| | 截图 | 我们 |
|---|---|---|
| 成本 | 零 | 有 |
| **出错风险** | **零**（那就是原图） | **有**（AI 会读错） |
| 讲得清吗 | 讲不清 | 能讲 |
| 改得动吗 | 改不动 | 能改 |

⚠️ **截图唯一的优势是绝对可信。一旦在"可信"上失守，用户就回去截图了，而且毫无心理负担。**

### 3. 行业知识只用来"帮 AI 读懂"

**来源：AI 预训练里的常识**（不外加知识库）。

⚠️ 行业知识属于**最弱的一档**（"行内常识补的"——原件里没有，是外部知识）。所以只有一种正确用法：

> **它生成假说，不提供答案。**
> 比如不是「电信里这个圆柱就是基站」，而是「看到『柱体 + 云 + 箭头』这种组合，先去查柱体上有没有文字、箭头两端有没有标签——**如果都没有，它更可能是故意留空，不是我没读到**」。

**所以行业知识以"提问模板 + 该去哪查"的形式存在，不以"结论"的形式存在。**
**放在 `references/` 里，按"看到什么"索引，不按"哪个行业"索引**——因为用户不会告诉你这是哪个行业的图，而判断行业本身又是一次不可靠的推断。

⚠️ **风险组合**：AI 自带常识 + 用户（售前）不懂那个行业 = **最危险的组合**。语言模型会流畅地编出行业解释，用户识别不出来，而这图会拿去给客户讲。所以必须：**每条假说带"怎么证伪它"；原件证据和 AI 的猜测分开摆给用户看。**

### 4. 讨论的深度：动态决定

判据不能只有"材料质量"，还有第二个变量：

| | 信息在原件里吗 | 用户知道答案吗 |
|---|---|---|
| 竞品扒来的高清图 | 在（但可能是误导） | **不知道** ← 售前常态 |
| 用户自己做的糊截图 | 不在 | **知道** |

⚠️ **第二维在开局是未知的**，所以只能**过程中逐步升级**，不能开局定死。

⚠️ **降级路径**（售前场景下应该成为默认）：

```
问事实：这条线是什么意思？        → 售前答不出（他也不懂原文）
   ↓ 自动降级
问取舍：这块你想保留还是砍掉？      → 售前答得出（他知道自己的方案要什么）
```

**售前不知道原文什么意思，但一定知道自己的方案要什么。**

### 5. 开局：先问一句

用户什么都不说、丢一张图进来，**第一句话是**：

> **你要我理解的是哪一块？要重画的是哪一块？**

⚠️ 这**不违背"打败截图"**——它不是让用户填表、也不是让他描述风格，**只是让他指一下**，成本几乎和截图一样低。

⚠️ 但必须是**两句**——因为 **要理解的范围 ≠ 要重画的范围**，而且 **理解 ⊇ 重画**。
（真实案例：第 6 页那个案例里，理解范围是**整页**——左边流程图要靠右上文字卡对照才读得懂；重画范围只是**左下角那一块**。）

## 十、架构

### 形状

```
宿主 agent（Claude Code / Codex）
│
├── skill  redraw-diagram        ← 产品本体，走 ①→⑥
│     SKILL.md
│     references/
│       reading-rules.md           读图纪律（核心资产）
│       ask-when.md                什么时候问
│       industry-hypotheses.md     行业假说（按"看到什么"索引）
│
├── skill  verify-redraw         ← ★ 第二双眼睛（见 §十.5）
│
└── scripts/  代码（干精确活）
      输入适配器   read_pptx_shapes / read_smartart / read_image / read_pdf / read_text
      中间模型     schema + 校验器
      输出序列化   build_pptx / build_svg / ...
      对账工具     Check A / Check B（见 §十.5）
```

### 1. 中间模型有两层

| | 装什么 | 谁来定 |
|---|---|---|
| **层 1：在说什么** | 有哪几个东西、它们是什么、谁连着谁、**每条信息的来源** | **事实** → 要用户确认 |
| **层 2：长什么样** | 每个东西在哪儿、多大、什么颜色、什么样式 | **审美** → AI 自己定 |

**为什么必须分两层：**

- PPT / SVG **两层都要**——没有位置画不出来
- Mermaid **只要层 1**——位置它自己排
- **"这条是我推的"只能装在层 1**——它是关于**意思**的，不是关于位置的

**两层之间那条线，就是"用户要确认的"和"AI 自己决定的"的分界线**——正好对上项目最早定的分工原则：**审美放手，事实抓紧。**

### 2. 层 2 不是"不讨论"，是"只讨论约束和取舍"

判据还是那一条：**答案在不在用户那儿？**

| | 答案在图上吗 | 用户知道吗 | 问不问 |
|---|---|---|---|
| 用什么蓝、间距多少、圆角多大 | 没有 | **他也不在乎** | ❌ 不问，问了是打扰 |
| **跟不跟你的模板** | 没有 | **只有他知道** | ✅ **必须问** |

**层 2 里必须问的四类：**

1. **外部约束**（跟不跟你的模板 / 品牌色 / 客户有没有指定）
2. **交付形态**（PPT 可编辑 / SVG / 都要）
3. **表达方式**（画成泳道图还是框线图——**图型不是审美，是表达**）
4. **原件版面有毛病**（重叠、溢出、挤成一团——照抄还是修好）

**不问的**：配色、间距、字号、圆角、线粗、对齐方式、箭头样式。

⚠️ **"不问" ≠ "不给你看"。** 放手不是藏起来，是**不问你，但做出来给你看；你不同意就说**。和"标号图"是同一个手段。

⚠️ **层 2 和层 1 不是单向的**：
- **层 2 乱 → 层 1 读错**（两个框重叠，可能读成三个）
- **排版会反过来暴露层 1 的缺口**（要摆位置时才发现"这俩什么关系我不知道"）→ 排不下去时，正确动作是**回头问**，不是硬排

### 3. 清单是「台账」，不是「最终答案」

**改它是追加，不是覆盖。**

用户说"这个空框里其实是审批"时：

```
原件我读到的：  这个框是空的      ← 保留，不抹掉
你说的：        里面是"审批"      ← 新增一条证据
最终要画的：    审批
```

**为什么不能覆盖：**
1. **用户可能记错。** 抹掉了"原件是空框"，就再也回不去了
2. **"原件如此"和"你要我这么画"是两件事**——交付时要告诉你"我改了原件的什么"，分不清就说不出来

> **已栽过一次**：用户答"是一条**折线**关系"，被记成"**关系数 = 10**"。
> 那次能发现错误，**唯一的原因是原话没被解读覆盖掉**。

### 4. 产物：1 份权威 + 3 个视图 + 1 份台账

```
        ┌──────────────────────────────────┐
        │   spec.json   结构化清单（唯一权威）│   ← 只有它能被编辑
        │   条目 + 来源标记 + 坐标 + 关系     │
        └──────────────────────────────────┘
               │                      │
      渲染 ────┘                      └──── 渲染
         ▼                                ▼
   spec.md                            marked.png
   给人看「内容」                      给人看「位置」
   ✋ 不许直接改                       ✋ 不许直接改
```

| 文件 | 性质 | 给人看什么 | 能改吗 |
|---|---|---|---|
| `spec.json` | ★ **唯一权威** | —— | ✅ 只有它 |
| `spec.md` | 视图（渲染出来） | **内容**对不对 | ❌ |
| `marked.png` | 视图（渲染出来） | **位置**对不对 | ❌ |
| 变更说明 | 视图（交付时渲染） | **我改了你原件的什么** | ❌ |
| `transcript.jsonl` | **台账（追加型）** | 用户原话 | ❌ 只增不改 |

⚠️ **两个视图不是"两份内容"，是同一份内容的两种呈现。** 当成独立产物，早晚会出现"markdown 说的和 json 存的不一样"。

⚠️ **证据只增不改，结论可以重整。** 清单会被重整（合并条目、调顺序、改结构），重整时**最容易被顺手改掉的就是用户原话**——所以原话必须单独放一份追加型台账，清单里的条目**引用**它的编号。

⚠️ **标号图 + markdown 是一套**：**标号图给人看位置，markdown 给人看内容。两个合起来才是完整的核对界面。**

⚠️ **人看的视图必须能读，JSON 不行。** 但用户**不直接改视图**——用户说"第 3 条不对"，改的是 `spec.json`，然后重新渲染视图。

### 5. 自检：两道检查，都是「逐条对账」，不是「逐像素差分」

| | 对什么 | 什么时候能做 | 查的是 | 需要 AI 的眼睛吗 |
|---|---|---|---|---|
| **Check A** | **输出 vs 清单** | **永远能做** | **执行有没有走样**（画错 / 画漏 / 画多） | ❌ 不需要，两边都能机器读 |
| **Check B** | 清单里**标为「来自原件」**的条目 vs 原件 | **有原件时** | **我读错了没有** | 文字、个数 ❌<br>关系 ✅ 需要独立读者 |

**两条合起来，文字这一块可以做成全机器验证：**

```
输出 = 清单      （Check A，机器）
清单 = 原件      （Check B，机器——文字直接从 PPTX/SmartArt/PDF 里提取）
⟹ 输出 = 原件   一个错字都跑不掉，完全不经过 AI 的眼睛
```

⚠️ **Check B 只覆盖"标为来自原件"的条目。** 用户改过的条目（来源已变成"用户说的"）**不进 Check B**——它们和原件不一样是**应该的**。
"把别人的图变成自己的图"这件事，**核心就是要有意地偏离原件**，所以"以原件为准"从根上就错了。

⚠️ **对账会查出原件自己的错别字。** 那不是 bug，是**发现**——原样照抄，然后告诉用户"这里我没动，你要不要改"。两种结果绝不能混：
- **我和原件不一致** → 我们画错了
- **原件本身有问题** → 是发现，报给用户

⚠️ **入8（图片）天生更弱**：没有文字层，Check B 只能靠 OCR——**又变回 AI 的眼睛了**。

### 6. work/ 目录

```
work/
  source/          素材原件（只读，永不修改）
  spec.json        ★ 结构化清单（唯一权威）
  spec.md          ← 从 spec.json 渲染，给人读
  marked.png       ← 从 spec.json + 原件渲染，给人看位置
  transcript.jsonl ← 用户原话（追加型，只增不改）
  rendered/        原件的渲染图（可随时重生成，算缓存）
  out/             交付物（pptx / svg）
  checks/          自检报告（Check A / Check B）
```

### 7. 画：两个出口各自序列化

**第一版是「清单 → 两条独立的序列化器」，中间不做格式转换。**

```
            spec.json（清单）
            │              │
      build_pptx()     build_svg()
            ▼              ▼
         out.pptx       out.svg
```

⚠️ **两条路的工作量分布完全不同**，这不是实现问题，是格式本质：

| | PPTX / DrawingML | SVG |
|---|---|---|
| 预设形状库 | **182 种**现成可用 | **没有**，只有 rect / circle / line / path |
| 文字排版 | **自动**（换行、居中） | **没有**，一行一行给坐标 |
| 主题色 | 有 | 没有，只能绝对色 |
| 坐标单位 | EMU | px |

> **PPTX 是"声明式"的**（说个圆角矩形，位置文字它帮你摆）；
> **SVG 是"命令式"的**（每根线每行字的坐标都得你算）。

⚠️ **187 个预设几何不要自己写**——用现成的（Apache POI 数据，Apache-2.0，含公式求值器和语义词表）。
详见 [实测与调研 §四](实测与调研.md)。

⚠️ **什么时候这条路线要重估**：一旦支持"从零画"（入6）或 Mermaid 输出（需要自动排版），"用中间格式"那条路的取舍就变了。同样见 [实测与调研 §四](实测与调研.md)。

### 8. 已定的决定

| # | 决定 | 为什么 |
|---|---|---|
| 1 | **验收必须是"另一双眼睛"**——用宿主**自带**的通用 subagent，不共享上下文 | **坑 A**（见 [实测与调研 §一](实测与调研.md)）：同一个 agent 用自己的理解检查自己，对这类错免疫。不写自定义 agent 定义，是为了双生态兼容 |
| 2 | **中间模型 = 磁盘上的结构化文件 + 对话里的自然语言**，两者是**同一份东西的两种呈现** | 机器要精确可校验，人要能懂。**对话里的话必须从文件生成**，不能并行维护 |
| 3 | **三个正交部分：输入适配器 × 中间模型 × 输出序列化器** | "场景可以不断丰富"在架构上的落地。**新加一种输入/输出，不该动中间模型** |
| 4 | **代码边界**：能用代码验的不交给 agent 判断；需要"看"和"取舍"的不硬编码 | 精确活要可复现、可查错 |
| 5 | **凡是 agent"读"出来的东西，都要有一个代码可复核的落点** | 自检要独立，前提是有一部分东西不依赖 agent 的眼睛 |
| 6 | **文档分三种，别混**：说明书（不变）／ 工作台（每次任务变）／ 行业假说（一直加） | 生命周期完全不同，混着放会互相污染 |
| 7 | **推断只允许在"读"那一步发生，而且必须留痕**——序列化阶段绝不引入新的判断 | 能读到的就读（PPTX / SmartArt 里 `prstGeom` 是明写的），读不到才推（图片），而且推的要标成"我推的" |

### 9. 责任怎么分

> **用户负责"你要什么"；我们负责"我读对了没有"。**
> 这两件事不能互相顶替。

⚠️ 把"读对了没有"整个推给用户，等于**把产品的生死押在用户的注意力上**——而"售前扫一眼标号图说对、其实没细看"是常态。Check B 是**不依赖用户注意力的兜底**，而且它免费。

## 十一、错误类型：什么错了算「要命」

> ⚠️ 这一节是**我方提案**，还没拿真售前验证过。

| # | 错误类型 | 例子 | 后果 | 能自动查吗 |
|---|---|---|---|---|
| 1 | **文字写错 / 漏 / 多** | 「两地**三**中心」→「两地**两**中心」 | 🔴 **会说错话，可能担责** | ✅ **能，且能 100% 查** |
| 2 | **元素多一个** | 多画了一个客户根本没有的模块 | 🔴 **等于承诺了不存在的东西** | ✅ 能 |
| 3 | **元素少一个** | 漏了「安全审计」这一层 | 🔴 客户追问时**答不上来** | ✅ 能 |
| 4 | **关系错** | 箭头方向反 / 连错对象 | 🔴 **整张图的意思反了** | 🟠 能，看有没有独立来源 |
| 5 | 形状身份错 | 菱形（判断）画成方框 | 🟠 形状**有含义时**算第 1 类；没含义时无所谓 | 🟡 只能和自己的读法比 |
| 6 | 分组 / 层级错 | 同一泳道的东西被分开 | 🟠 会被追问 | 🟡 部分 |
| 7 | 位置 / 版面 | 整体偏几像素、间距不匀 | ⚪ 不会讲错，但显得不专业 | ⚪ 能测，但**不该测** |
| 8 | 颜色 / 字体 | 和公司模板不一致 | 🟠 **有模板要求时在乎** | 🟡 需要用户先给模板 |

### 这张表最要紧的一件事

**第 3 列和第 4 列正好是反的：**

| | 要命的（1–4） | 无所谓的（7–8） |
|---|---|---|
| 性质 | **离散的、内容性的** | **连续的、形式性的** |
| 例子 | 一个字符串、一个个数、一组边 | 一个偏移量、一个色值 |
| 怎么查 | ✅ **逐条对账** | 只能逐像素差分 |

> **像素差这个工具，恰好只能测那些没人在乎的东西；真正要命的那些，它一个都测不出来。**

**这就是为什么"像素差"不该当判据——不是不够准，是方向就错了。**

⚠️ **真正的问法不是「多像才算够」，是「错在哪里绝对不能忍」。**
用户的容忍度是**不对称的**：不好看能忍，讲错了不能忍——因为**这张图要拿去给客户讲，讲错了要担责任**。

⚠️ **为什么这条决定产品成不成立：退路是零成本的。** 用户只要觉得"还得再核一遍才敢用"，就回去截图了——成本是 Cmd+C / Cmd+V。
