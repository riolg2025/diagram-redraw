# 需求确认稿 v0.1

> 这一页是**理解**，不是设计。如果哪条不对，改这一页。

## 一句话

**给 AI 一张现成的图（或一段描述），让它和用户来回问清楚，然后把这张图重画成可查看、可编辑的形式。**

痛点不在"画不出来"，在**"AI 理解得和人不一样"**。

## 场景

**输入**（三种，来源五花八门，**不标准是常态**）：

- PPT 里指定的某一页（可能是原生形状，也可能整页就是一张位图）
- Markdown（用文字描述一张图）
- 一张图片文件

**输出**（两种）：

- SVG
- **PPT 里可编辑的形状和文字**（不是一张图）

## 流程：先问清楚，再画

```
给输入
  ↓
先确认：要理解的是什么、要重画的又是什么   ← 第一位，见下
  ↓
我先自己读（尽量读懂，但绝不编）
  ↓
把读到的标在原图上给你确认   ← 第二个抓手
  ↓
来回问几轮，把任务和意图问清楚
  ↓
画
  ↓
不确定的地方标在图上，你一眼看得见
  ↓
改 / 完成
```

**不是"上来就画"。** 但也**不是"问一堆风格问题"**——见下面的分工。

### 为什么"确认范围"排在第一位

真实场景里，**用户给的那一页里，图往往只是其中一部分**。第 6 页就是活例子：同一页上有

- 左边的流程图（**要重画的就是它**）
- 右上角的文字卡片（1–5 条）
- 右下角一堆界面截图

如果一上来就把"这一页"当成重画对象，会有两个后果：把文字卡片也画进去（多余），
以及**画不出那些截图**（它们是位图，不是形状），最后交出一个残废东西，
而用户想要的那张图**根本不在里面**。

所以第一句话不该是"我看到了什么"，而是**"你要我理解的是哪一块、要重画的是哪一块"**。

## 三条硬要求

1. **意图一致** —— 重画出来的图，说的还是原图那件事。
2. **元素不增不减** —— 一个不多、一个不少。AI 不许想当然地合并、拆分、补充、删掉。

   ⚠️ 但"数什么"得说清楚。第 6 页实测：**11 个线条对象，却只有 10 条关系**
   （两条折线其实是同一条，经用户确认）。两个数都对，只是数的东西不一样。
   **规矩：按"关系"数**（人看图看到的是"10 条箭头"），**但两个数都报出来**——
   否则"11 个对象画成 10 条箭头"看起来像丢了一条。
3. **要改先问** —— 觉得该增减，或者看不清，**先问**，不许自己定。

   ⚠️ 这条包括**原件的毛病**。第 6 页原文有两处错（编号 1,2,3,3,4,5 重复；
   步骤 6 写成"开发环境"却站在测试环境上方）。重画时**原样照抄、一处不改**，
   然后告诉用户"这两处我没动，你要不要改"。


## 一条分工原则

> **审美放手，事实抓紧。**

| | 规则 |
|---|---|
| 好不好看、用什么配色、怎么排版 | **AI 自己决定，越少给规则越好** |
| 有没有编、有没有增减、要不要问 | **一条都不能少** |

理由：售前最大的风险不是图丑，是**图错了但他没发现，然后拿去给客户讲了**。

## 另一条：用户的回答，我不许自己解释

空跑 01 里真犯了一次。

```
我问的：C10 和 C11 算一条关系还是两条？
用户答的：是一条折线关系          ← 原话
我记的：  关系数 = 10             ← 这一步是我自己挑的解释，错的
```

"折线"说的是**形状弯了**，我问的是**关系数量**。用户答的没错，是**我的问题本身有歧义**，
而我没有回问，挑了一个方便自己的解释当成事实记了下来。

**两条规矩：**

1. **回答也可能是歧义的。不许自己择一，要回问。**
   尤其当对方用的词，和问题的问法不是同一个维度时（这里：形状 vs 数量）。
2. **回答必须逐字留档，和我的解读分开存。**
   这次能发现错误，唯一的原因是**原话没被我的解读覆盖掉**。

## 用户是谁

**经常做 PPT 的售前 / 运营。**

这决定了三件事：

- **他们不看技术报告。** 所以"哪里不确定"必须**画在图上**，不是列在文档里。
- **他们眼睛很毒，但不懂技术。** 所以"标号图让你确认"这种开场最合用——不用想、不用打字、不用描述风格。
- **图往往不是他们自己画的**（客户给的、竞品扒的、同事传的）。所以"问意图"经常问不出东西，**"我标出来你自己看"才是主力**。

## 交付形态

**一个 GitHub 仓库，开源，Claude Code 和 Codex 都能装。**

- 技能格式（`SKILL.md`）两边是**同一个开放标准**，一份说明书通用
- OpenAI 那边**主动兼容** Claude 的清单格式，所以一个仓库两边都能装
- **不做图形界面，不做服务器**——装完就在 Claude Code / Codex 里用
- ⚠️ 别指望上 OpenAI 的公共插件目录：它明确不欢迎需要读本地文件、跑本地脚本的插件。**走 GitHub 直接装**

三样东西：

```
一份说明书（读图该守什么规矩、什么时候停下问）
一组能干精确活的小脚本（量像素、读坐标、追连线）
可插拔的行业知识包（跨行业的关键，核心保持干净）
```

## 已知的坑（不解决会白干）

| 坑 | 说明 |
|---|---|
| **渲染是空白的** | 这次实测：bundled LibreOffice 直接渲染这份 PPT 的 6 页，全部空白（六页字节数一模一样）。必须**先转 PDF 再取图**才行 |
| **中文字体缺失** | 渲染时缺 `微软雅黑`、`inpin heiti` 等，会**改变文字排版**。看到的和原作者看到的不是一回事 |
| **组内坐标不可直接用** | 组里的元素坐标是**组内相对坐标**，不是页面绝对坐标。不做变换就会算到页面外面去 |
| **开源素材** | 用户已确认这份测试 PPT 可以公开。但只有一份不够，还需要更多种类的公开样例 |

## 还没定的

- 输出 PPT 时，是"在原文件上改"还是"新建一份"（现在是新建）
- SVG 和 PPT 两条输出，先做哪条
- 行业知识包长什么样、怎么装

## 空有三种，含义完全不同（空跑 02 新增）

第 5 页 B 区里，6 个流程框 + 2 个菱形**一个字都没有**。核实后确认：**这是作者故意的。**

| 种类 | 含义 | 处置 |
|---|---|---|
| **我没读出来** | 我的问题 | 去查，一个字都不许问用户 |
| **原件里没有** | 缺失，本身是证据 | 记下来，标"原件没说" |
| **原件故意留空** | **"这里放的是你自己定义的任意步骤"** | **一个字都不许填** |

第三种之前完全没考虑过。而它最危险——**填上名字，元素数没变，但图的定位被改了**
（从"卖能力"变成"卖一个具体流程"），**等于把作者的意图改了**。

### 怎么分辨？靠对照，不靠这张图本身

- **同一张图里的对照**：B 组里"工具服务层/执行层"全部具名，"流程引擎层"全部留空——
  说明分界线不是随机的。
- **跨页的对照**：第 6 页那张流程图**每步都写满**（1.代码构建 → 8.部署到生产环境），
  因为那页讲的是**一个具体流程**；第 5 页讲的是**引擎的能力**。

→ **有些意思只能从对照里读出来。** 单看一张图永远读不出"空白 = 由你定义"。

### 所以"用上下文"的具体形式

不是"多给点背景资料"，而是：**主动去找对照**——同一页内部的对照、其他页的对照、
同类图的对照。**对照才是让空白开口说话的东西。**

### 一条附带的方法：编号可以，命名不行

在标号图上给空框编号（N1、N2）是**指代**，方便用户指着说"这个"；
**给它们起名字，就是把我的理解冒充成图上的内容。**

## 观察到的作者习惯（空跑 02）——**这是假设，不是铁律**

> ⚠️ **别把下面这张表当规矩用。**
> 每张表的作者都有自己的习惯，记死了只会限制自己，而且规则越攒越多、迟早打架。
> **正确的姿势是"不懂就问"，这张表最多算参考。**
> 它自己也当场给出了反例：同一页里 D1 和 D2/D3 的虚线样式都不一致（作者笔误），
> 而"黄色"其实是主题强调色，换一份 PPT 就换一个颜色。
>
> **只有"关于我自己怎么读"的规矩才能记死**（比如"方向和箭头个数必须放大看"）。
> **"这个作者什么意思"永远只能当假设。**

第 5 页 B 区里，作者用**线型和颜色**承载了不同的意思。用户已确认：

| 视觉特征 | 意思 | 证据 |
|---|---|---|
| **实线** | 同一层内的流程走向 | 流程图主链（16 条 0.8pt 实线） |
| **虚线** | **另一种关系**——异步 / 人工介入 / 子流程调用（都有） | D2、D3（1.5pt `dash`）；D1（2.2pt `sysDash`）|
| **粗黑箭头** | **跨层**（流程引擎层 → 工具服务层） | T1，黑色、明显粗于其他 |
| **强调色（黄 #F1B700）** | **关系 / 后续路径** | Y1（组对组双向）、Y2（后续路径） |
| **两端带箭头的黑线** | **一对一的双向** | W1、W2 |
| **大括号** | **分组**——把几个方块括成一组 | K1、K2 |

### ⚠️ 这套语法目前**只有第 5 页一处证据**

拿整份 PPT 扫了一遍：

```
第 1、2、3、4 页   没有任何连接线（第 2 页只有 8 个独立箭头形状）
第 5 页            16 实线 / 1 sysDash / 2 dash / 2 大括号 / 3 上下箭头 / 1 粗箭头 / 1 右箭头
第 6 页            全部实线，蓝色 #0084CF，无虚线、无大括号、无强调色
```

**所以"虚线 = 另一种关系"这条，只有第 5 页一个实例。**
没有第二页能证实它，也没有任何一页能否证它。
→ 这正是这个项目反复栽的坑：**只在一张图上验证。** 记下来，别当成定论。

### ⚠️ "黄色"不是黄色，是**主题强调色**

Y1/Y2 用的是 `schemeClr accent3`，这份主题里恰好是 #F1B700。
**换一份 PPT，同一个"强调色"可能是蓝的、红的。**
所以重画时不能写死黄——要认成"**这份主题的强调色**"，然后按主题取色。

同理 D1 的 `sysDash` 与 D2/D3 的 `dash` 不一致，**用户已确认是笔误，没有讲究**。

## 一个我自己撤回的结论：「原件容易读错」

**这条本来是错的，撤回。但过程留着，它比结论有用。**

我一度把"两个大括号 + 一根箭头"读成"分组"，准备写成"原件表达不清"。
**7 倍放大之后发现：那根黄色箭头本来就是两头都有箭头的双向箭头（`upDownArrow`），
两个大括号的尖正好对着它。原图的表达是清楚的，设计还挺讲究。**

**真正的错因是分辨率。** 全页视图下那根箭头只有 16×50 px，两个箭头头部各约 7 px，
我把它看成了"朝下的单箭头"。

### 所以要记的规矩是这条

> **「方向」「箭头个数」这类判断，禁止在全页视图上做，必须放大到能看清箭头头部。**

**这是同一个错法在这一轮里的第二次**：第 2 页那个 `rot=180°` 的右箭头，
也是"不放大就会把方向读反"。两次指向同一条规矩。

### 更值钱的一条：别急着把锅推给原件

在核实之前，我已经写好了一段"原件表达不清"的分析，还配了一句挺像样的总结——
"一种表达方式，连一个认真读的读者都读错了，那它就不够清楚"。

**这句话本身没错，但用错了地方。** 而它特别危险，因为：

- 它听起来很专业、很体谅用户
- 它把**我的失误**包装成了**原件的缺陷**
- 一旦写进交付物，作者会被要求去改一个本来没毛病的地方

这正是"去查"的第二种形态：**回去看原件 vs 回去修我自己。** 我差点选了前者。

→ **规矩：怀疑原件之前，先放大到极限再看一遍。**

### 但有一条真实的观察，可以留着

那根双向箭头确实**又短又细**（16×50 px，"双向"这个信息在整页视图下容易丢）。
这不算缺陷，但如果你希望它在投影时更醒目，可以稍微放大一点。**这是可选项，不是必须改。**
