## ★ 我撤回了一个结论

我一度把"两个大括号 + 一根箭头"读成"分组"，准备写成**"原件表达不清"**，
还配了句挺像样的总结（"连一个认真读的读者都读错了，那它就不够清楚"）。

**7 倍放大之后发现：那根黄色箭头本来就是两头都有箭头的双向箭头（`upDownArrow`）。
原图的表达是清楚的，设计还挺讲究。**

**错因是分辨率**：全页视图下那根箭头只有 16×50 px，两个箭头头部各约 7 px。

→ 变成一条**能记死的**规矩：

> **「方向」「箭头个数」这类判断，禁止在全页视图上做，必须放大到能看清箭头头部。**

**这是同一错法在这一轮里的第二次**（第 2 页 `rot=180°` 的右箭头也是"不放大就读反"）。

→ 还有一条更值钱的：**别急着把锅推给原件。**
那段"原件表达不清"写得很专业、很体谅用户，**实际是把我的失误包装成了原件的缺陷**。
这正是"去查"的第二种：**回去看原件 vs 回去修我自己。我差点选了前者。**
**规矩：怀疑原件之前，先放大到极限再看一遍。**

# 第三轮：用户反馈后的修复

用户看了 PPT 和 SVG，报了两个问题。**两个都查到了根因，不是我猜的。**

## 问题 2：文字压住边框

**根因不在文字，在描边。** 逐行扫描框下沿发现：

```
原图  1 行（y=587）
我的  2 行（y=587,588）
```

原图所有形状的描边宽度都是 **0.5pt（=1px @150dpi）**，我用了 0.9pt（≈2px）。
文字位置其实**一行不差**（墨迹都在 y 557–586）。

→ **边框粗了一倍，看起来才像"压住了"。**

**教训**：眼睛看到"文字压边框"，会本能地去调文字位置。**实际该量的是线宽。**
先量，再改；不然会改错东西。

## 问题 1：SVG 和预览不一致

**我从来没渲染成功过 SVG**（这套工具不支持 `svg → 图`），所以三处 bug 一直没被发现：

| bug | 症状 |
|---|---|
| **漏了 `<defs><marker>`** | 16 处 `marker-end` 全指向不存在的标记 → **箭头全没了** |
| **字号写死 13/15** | PPTX 用 9pt/10pt（≈18.75/20.83px），SVG 小了三成 |
| **描边按 pt 当 px 写** | SVG 坐标是 px，线宽得 ×150/72 |

修完复查：`<marker>` 1 个 / 引用 16 次 ✓，字号 18.75×13 + 20.83×11 ✓。

**教训**：**不能亲眼验证的输出，必须做源码级的逐项检查。**
我这次是靠 `grep` 数出来的（`<marker>` 定义数 vs 引用数）。

## 顺带找出来的另外两处（用户没提，但确实不一致）

用**差分图**（原图 vs 重画，逐像素）找到的，眼睛看不出来：

| 差异 | 根因 |
|---|---|
| 所有文字有水平"重影" | 原图文本框用 **OOXML 默认内边距**（左 15px、上 7.5px），我设成了 0 |
| 方块字号偏大、`Powershell服务` 多余换行 | 原图是 **8pt**（我用了 9pt）；而且中文要显式设 **`ea`（东亚）字体**，只设 `latin` 会回落 |

差分图指标：**平均差 28.7 → 24.8；显著差异像素 9.6% → 8.0%**。

剩下的 8% 大部分是**边框 1px 取整偏移**，消不掉；
另一部分是**字体替换**——渲染环境里没有 `微软雅黑`，LibreOffice 会替换成别的字体。
**用户机器上装了微软雅黑的话，这部分差异会消失。**

## 这次学到的方法（比修复本身值钱）

1. **先量，再改。** 看着像文字的问题，可能是线宽。
2. **差分图能看见眼睛看不见的东西。** 文字"重影"、1px 偏移，全靠它。
3. **不能渲染的输出，就做源码级检查**（计数、比对字段）。
4. **同一个坐标换算，我错了三次**（组变换漏减 chOff、new/orig 方向搞反、SVG 的 pt/px）。
   → **坐标换算不许手算，一律让脚本按数据算。**

# 第四轮：SVG 的三处错（用户第二轮反馈）

用户报：**K1/K2 大括号不对，Y1 和 W1/W2 双向箭头是单向的。**

## 根因（都在我手画的 SVG 路径里）

| 症状 | 我画错在哪 |
|---|---|
| 双向箭头是单向的 | `upDownArrow` 的路径顶点顺序画成了"一个朝下箭头 + 两个倒钩"，根本不是双箭头 |
| 大括号不对 | 画成了**两条各管一半的小曲线**；而且长度取错字段（旋转后长度在 `height` 不在 `width`） |

修法：双向箭头改成"两个尖 + 中间一根杆"的十顶点路径；括号改成"横线 + 中间一个直角尖"，
朝向用原图验过（`rot=90` 尖朝上、`rot=270` 尖朝下）。

## ★ 这一轮最值钱的教训：我在盲改一个没运行的脚本

插代码时破坏了缩进，脚本报 `IndentationError` **直接不执行**。
而我把报错 `2>&1 >/dev/null` 掉了，**什么都没看见**。后果：

- 以为改了，其实一行都没生效
- 反复渲染的是**上一次的旧文件**，还据此"验证"了好几轮

**是渲染产物的 sha256 一直不变，才把它抓出来的。**

→ 两条死规矩：

1. **构建脚本的 stderr 绝不许吞掉。**
2. **每轮必须验"产物真的变了"**（比哈希 / 比 mtime / grep 关键字段），
   不能只看命令有没有报错。

## 顺带修的：连线取色原则

原来的做法是"从渲染图里采最深的像素"。问题是**穿过的元素会污染采样**——
一条深蓝分隔线被黄箭头穿过，就采成了黄色。

改成：

> **原图 XML 里显式写了颜色 → 用它。**
> **只有没写（继承主题）时才去渲染图里采。**

这条更本质：XML 里的值是**原件的事实**，采样只是**渲染的近似**。
